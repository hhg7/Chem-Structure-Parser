
# What the C is worth

`benchmark.pl` measures it rather than asserting it. Against a pure-Perl
reader that slices the same columns in the same order and builds the same
nested hash — not a straw man, just the same job done per line in Perl —
reading 200 structures from PDBbind v2020, best of three:

    structure_info, features => 0            4.81 s     221,000 atoms/s
    structure_info, atoms => 0               3.55 s     299,000 atoms/s
    the XS parse alone                       1.51 s     704,000 atoms/s
    the same reader, in pure Perl            5.32 s     198,000 atoms/s
    pure Perl, and the same statistics       6.95 s     152,000 atoms/s

**The parse is 3.5x the same parse written in Perl.** That is what the C buys.

`structure_info()` as a whole lands at 1.1x the plain Perl reader and 1.4x the
one that also gathers the statistics — while doing a good deal more than
either: the header records, SEQRES, the gaps between the declared sequence and
the modelled one, chain typing, ligand and ion classification. Building a hash
of hashes out of what was read costs what it costs in any language, because
the hashes are the answer. Reading is the part worth writing in C, and reading
is the part that got faster.

Three rounds of that measurement changed the code. The first showed the whole
read coming out *slower* than the naive Perl reader, because every per-atom
statistic was being gathered in Perl over data C had just finished reading;
those moved into the parse. The second showed each atom being built twice —
once as columns in C, once as a hash in Perl — and the parse now builds the
hash itself, which took another 25% off both the time and the memory.

The third counted the SVs. A residue's identity — its name, its chain, its
number, its insertion code, whether it is a HETATM, which model it is in — was
built once per atom and read once per residue, and six strings and integers
per atom against six per residue was a third of everything the parse built.
Building it where it is read took the 200-file parse above from 1.95 s to
1.59 s and the peak memory of the largest entry in the set — 4fqr, 90,792
atoms — from 153 MB to 126 MB, and the whole `structure_info()` read of it
from 168 MB to 141 MB. A caller of the low-level parse who asks for columns
still gets one entry per atom, because there the columns are the answer;
`t/parse.t` reads four fixtures in both shapes and asserts they say the same
thing.

# What is written in C, and what is not

The C side makes one pass over the bytes and does three things: it splits
ATOM/HETATM records into parallel per-field arrays, it marks where each
residue begins and ends, and it groups every other record by record name for
Perl to take apart. Residue name lookup — three letters to one letter, and the
amino acid/nucleotide/water question — is a switch on three packed bytes, and
one table serves `aa3to1()`, `res1()` and `res_type()` so the three can never
disagree.

The per-atom result is columnar — one array per field rather than one hash per
atom — which is both faster to build and about an order of magnitude smaller
while it is being built. Perl turns it into the nested hash afterwards, and
only for the atoms that were kept. That is the shape a caller of the low-level
parse gets; when the caller wants the atom hashes, the parse builds those
directly and emits the residue's identity once per residue rather than once per
atom, which is where Perl reads it either way.

Everything else is Perl. The header records are irregular, they are a few
dozen lines per file rather than hundreds of thousands, and they are where the
next surprise will turn up; none of that is worth writing in C.

Two details in there are worth knowing about, because they are where a PDB
reader is usually wrong:

**Coordinates.** `x`, `y` and `z` are adjacent eight-column fields with no
separator between them, so a reader that scans for a number instead of slicing
the columns runs `-12.500 111.000` together. They are sliced, and converted
with `strtod` on the slice.

**Elements.** Columns 77-78 hold the element symbol, and when they are missing
— older files, and files written by programs that should know better — it has
to come from the atom name. A one-letter element is right-justified from
column 14, so ` CA ` is a carbon alpha, and a two-letter element starts in
column 13, so `CA  ` is a calcium. A hydrogen with a long name like `HG11`
also starts in column 13, and taking its first two letters makes it mercury;
what separates them is that it fills all four columns, which no two-letter
element's name does.

All three roads to a symbol shout it — the columns are capitals, mmCIF's
`type_symbol` is capitals as often as not, and the guess above uppercases what
it takes from the name — so the symbol is put back into IUPAC's case once,
where it is settled, and a zinc reads back as `Zn` whichever road it took.
Only the 118 named elements are corrected: a field that spells no element is
left as the file wrote it rather than dressed up as one.

# What the physical properties cost

`benchmark.pl` measures these too.  Over 60 structures of PDBbind v2020, with
everything the module computes by default:

    structure_info, features => 0     1.30 s    246,000 atoms/s
    structure_info, the default      10.77 s     29,700 atoms/s    8.3x
      ... with interface => 0        10.02 s     32,000 atoms/s    7.7x
      ... with sasa => 0              3.80 s     84,000 atoms/s    2.9x

So the properties cost eight times the read, and **nearly all of that is the
surface**: everything else together -- the shape, the torsion angles, the
contacts, the exposure, the hydrogen bonds, the secondary structure, the
disulfides and the ring geometry -- comes to 2.9x the read between them.

The per-chain runs that give the buried area used to be a third of what the
properties cost and are now a fourteenth -- 0.75 s of the 10.77 above, where
they were 5.7 s of 16.38.  An atom's surface is decided by the atoms whose spheres reach it, so
an atom with no neighbour outside its own chain has the same surface with the
other chains there and taken away; the whole-structure run marks the ones that
do have such a neighbour, and only those are computed again.  `interface` stays
an option because it is still the difference between one surface and two, and
because a caller who does not want the buried area should not pay for it at
all.

That ratio is what decided where the work goes.

**The surface is the one place the C is not competing with a plausible Perl.**
960 sphere points per atom, each tested against that atom's neighbours, is
between one and ten million distance comparisons for a small protein.
`benchmark.pl` writes that loop out in Perl -- the same one mdtraj's kernel is,
neighbours by brute force and then points against neighbours -- and runs both on
the smallest structure of the set: 0.02 s against 1.95 s, a hundred times, for
the same 5661.25 A^2 to the last bit.  In Perl the whole set would be an hour.

Two things about the C are worth knowing, because they are where an
implementation of this is usually wrong or slow:

**The neighbour search is a grid, not a scan.** mdtraj compares every atom with
every other, which is fine for the few thousand atoms of an MD frame and is not
fine for a 400,000-atom entry -- 1.6e11 comparisons.  A grid of cells one cutoff
wide gives the same neighbour set from the 27 cells around each atom, in time
proportional to the number of atoms.  Measured: 6,432 atoms in 0.16 s and 16,399
in 0.40 s, which is 25 and 24 microseconds an atom -- flat, where a scan would
have cost the larger one two and a half times as much per atom.  `t/features.t`
is what says the two find the *same* neighbours: mdtraj's scan is exhaustive,
and every atom's surface matches it.  The same grid answers seven other
questions -- ring centroids, base centroids, sulphurs, CA atoms, heavy atoms,
contacts, and the CA atoms again for the secondary structure -- and
the bridge search in the secondary structure avoids one entirely by reading its
candidates out of the hydrogen bond list, which is linear in the bonds where the
obvious search is quadratic in the residues.

A grid is not enough on its own: the contacts walked it once per residue and
found that residue's own atoms by scanning the whole heavy-atom array, which is
residues times atoms and was 2.25 s of 4fqr's 11,406 residues and 88,416 heavy
atoms.  The atoms of a residue are one contiguous run of that array -- the walk
that built it went residue by residue -- so walking the run instead is 0.15 s
for the same pairs.

**The secondary structure counts the hydrogen bonds twice, on purpose.**
`structure_hbonds()` reports the bonds this module believes in -- a donor has to
be peptide-bonded to the residue its amide hydrogen was placed from -- and DSSP
is defined on the ones mdtraj finds, which has no such requirement.  Reusing one
table for both would mean either reporting bonds across chain breaks or
answering a different DSSP from mdtraj's, so there are two tables and two grid
walks.  It costs almost nothing: over 2AGV, 2,248 residues and 15,830 atoms, the
whole DSSP pass -- the second grid, the second table, the bridges, the ladders,
the helices, the bends and the hash of hashes -- is 0.021 s against 0.79 s for
everything the module computes by default, and 0.097 s for the parse itself.

**One walk, not nine.** The structure is a hash of chains of residues of atoms
and the arithmetic wants flat coordinate arrays, so `structure_features()`
flattens it once and hands the arrays to everything in turn.  Doing that in
Perl, or once per calculation, would rebuild the coordinate section nine times
over -- which is the mistake the second round of the parse benchmark found and
took out.

The hydropathy and the aromatic fraction are the exception and are in Perl: they
read a sequence string the chain already carries, which is a few hundred
characters and no per-atom work at all.

**Base stacking is in C for the grid rather than for the arithmetic.**  The
Condon score is a dozen floating point operations per pair, and it is the *pairs*
that are the work: 1JJ2, the large ribosomal subunit, has 2,872 nucleotides in
14,702 residues, and comparing every base with every other would be four million
pairs to reject.  Off the same grid the whole thing -- every base's centre of
mass and normal, then d0, omega, Xi and the score for the 2,853 pairs that are
within 5 A -- is 0.046 s, measured over three runs on a warm cache with
`store => 0`.  PDB_stacker, which is the Perl this is a translation of, is the
other end of that trade: it reads one tetramer per file and compares its four
bases pairwise, where a scan is the right answer and a grid would be overhead.

# What the RMSD costs, and why it is in C

`structure_rmsd()` is the one thing in the module that reads two structures at
once, and everything it does is per atom: pair them by chain, residue and atom
name; take the two centroids; take the inner-product matrix; and measure the
deviation with the rotation that came out of it.  Four passes over the paired
atoms, once per pair of structures -- and an NMR ensemble is not one pair but
190, because twenty models compared against each other is what an ensemble is
compared for.

`benchmark.pl` writes the same thing out in Perl, with the same quaternion
arithmetic, so that what is being measured is the language and not the method.
2L6J, 20 models of 1,841 atoms, 190 pairs:

    structure_rmsd                     0.05 s
    the same matrix, in pure Perl      1.19 s

**23x**, and the two answers differ by 1.95e-14 A at the worst pair.  Memory
goes the same way: over 2LL7, 20 models of 2,539 atoms, the comparison costs
3.4 MB above the structure in C and 6.5 MB in Perl (VmHWM, twice each).  Three
NV arrays and a 24-byte key per atom against four SVs per atom is the whole of
that difference.

Two decisions inside it are worth writing down.

**One walk per structure, not one per pair.** `set_build()` flattens each
structure into coordinate arrays once and the pairing keys are built and sorted
once; the 190 pairs are then 190 merges of two sorted lists.  Doing either per
pair would be twenty walks' worth of work done a hundred and ninety times, which
is the same mistake the parse benchmark found in a different place.

**The deviation is measured, not read off the eigenvalue.** This is the one
place where the module deliberately does *more* arithmetic than the reference
implementations do.  QCP's whole point is that it never forms the rotation:
`sqrt(2|E0 - L|/n)` falls out of the eigenvalue.  But E0 and L agree in as many
figures as the two structures do, so the subtraction throws those figures away
-- and two structures being nearly the same is the ordinary case, not the
pathological one.  Models 24 and 25 of 1JM4 in PDBbind v2020 have byte-identical
coordinates: gemmi 0.7.5, which takes the eigenvalue route, answers 8.6e-07 A
for them.  Measuring with the rotation costs one more pass over the paired atoms
-- included in the 0.05 s above -- has no cancellation in it at all, and answers
0.  Over 5,598 real superpositions the two routes agree to 5.65e-12 relative,
which is what `t/rmsd.t` holds them to.

**What is left is the walk, not the arithmetic.** Measured on this machine, gcc
`-O2 -Wall -Wextra`, perl 5.44.0 (`double`), lower quartile of 25 runs: one
pair of 4fqr (PDBbind v2020, 90,792 atoms each, the largest entry there) costs
0.065 s with `select => 'all'` and 0.052 s with `select => 'ca'` -- a selection
that keeps one atom in eight, for a fifth off the time, because both walk the
same atoms.  `fit => 0`, which drops two of the four passes, costs 0.059 s
against 0.065 s.  So the superposition is not where the time is: it is the
per-atom trip through the perl hashes, six or seven lookups an atom between
`set_build()` and `rmsd_keys()`, and the only speed-ups that show up in a
measurement are the ones that remove a lookup.  Three did, on the same
benchmark (`ens40` is the 40 models of 1H0T, 780 pairs; `4fqr` one pair of
90,792 atoms; seconds, before -> after):

    select    match   ens40              4fqr
    all       key     0.0324 -> 0.0311   0.0749 -> 0.0651
    all       order   0.0274 -> 0.0235   0.0704 -> 0.0417
    heavy     key     0.0233 -> 0.0224   0.0722 -> 0.0659
    heavy     order   0.0209 -> 0.0183   0.0646 -> 0.0473
    backbone  key     0.0180 -> 0.0171   0.0684 -> 0.0566
    backbone  order   0.0176 -> 0.0149   0.0651 -> 0.0430
    ca        key     0.0145 -> 0.0127   0.0622 -> 0.0515
    ca        order   0.0148 -> 0.0125   0.0611 -> 0.0419

They are: `set_build()` given a `coords_only` flag, which drops the element
fetch and the element-table search per atom along with the `rad`, `mass` and
`apolar` arrays nothing here reads; `rmsd_wanted()` taking the atom hash rather
than its element, so that the three selections which never look at an element
stop paying for the fetch; and `rmsd_keys()` told not to intern when the
pairing is `match => 'order'`, which compares no key at all.  Memory goes with
them: 17 bytes an atom for the three dropped arrays, in every structure of the
call at once, and the key list is given back down to the selection's size
rather than the atom count -- 24 bytes for every atom `select => 'ca'` left out.

**Two that did not show up, and are not there.** Packing an atom name into the
key's U32 instead of interning it through a hash -- four 7-bit characters and a
length fit in 30 bits -- measured 4% on `select => 'all', match => 'key'` and
under the run-to-run spread of the benchmark, for a bespoke encoding and a
different summation order in the answer.  A second copy of the deviation loop
with the identity rotation left out, for `fit => 0`, measured nothing at all:
the loop is bound by gathering `x[ia[i]]` out of three arrays, not by the nine
multiplies.  Both were written, measured and taken out again.
